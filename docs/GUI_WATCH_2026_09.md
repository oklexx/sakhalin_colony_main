# НАБЛЮДЕНИЕ ЗА ЧЕМПИОНОМ В GUI-ОКНЕ — протокол и диагностика (2026-09-20)

> Почему этот файл существует: «поставил галочку **GUI-окно** — и ничего не
> происходит, в логе тишина» невозможно было диагностировать удалённо, потому что
> протокол между `watch_champion.py` и raylib-окном нигде не описан, а все
> ошибки ожидания были бесконечными. Здесь — контракт сторон, таймауты, все
> известные причины молчания и то, что теперь пишет лог в каждом случае.
>
> Код: `watch_champion.py` (`run_visual_watch`), `src/gui.cpp`
> (`ai_read_action` / `ai_write_state`), `train_ui2/main_window.py`
> (вкладка «Наблюдение»). Регрессии: `tests/test_watch_visual.py` (18 тестов),
> `tests/cpp/gui_watch_check.cpp` (в `scripts/cpp_checks.sh`).

## 1. Что запускается

`python watch_champion.py --model-dir <dir> --visual` (в UI — галочка
**«GUI-окно»** на вкладке «Наблюдение») поднимает **двух участников**:

| Участник | Процесс | Роль |
|---|---|---|
| драйвер | `watch_champion.py` (Python, torch) | грузит политику, считает действие по `obs`/`action_mask` из `state.json` |
| окно | `sakhalin_colony_gui.exe --headless-ai` (C++/raylib) | держит симуляцию `Game`, рисует её, шагает по действию из `actions.txt` |

Симуляция живёт **в окне** (C++-ядро), а не в Python: наблюдение показывает
ровно ту игру, которую видит человек, но играет в неё модель. Поэтому налоговая
политика передаётся явно — `--tax-to-debt` (как в RL-среде), а не диалог налогов
(как в человеческом GUI): иначе модель «умирает» на 365-м дне там, где обучение
уже не умирает.

Окно ищется так (первое совпадение побеждает):

1. переменная окружения `COLONY_GUI_EXE` (полный путь к exe);
2. `PROJECT_ROOT/{., Release, build, build/Release, x64/Release,
   out/build/x64-Release, python}/{sakhalin_colony_gui.exe, SkhClny3.exe,
   colony_gui.exe}`.

Сборка окна: `build_gui.bat` (кладёт exe в корень проекта; нужен raylib из
`raylib/`). Внимание: `make gui` — это PySide6-дашборд обучения, а не C++-окно;
`make watch MODEL_DIR=…` запускает наблюдение в консоли (без `--visual`).
Если exe **старее** исходников `src/*.cpp`, драйвер пишет предупреждение
`WARNING: GUI exe собран ДО правок в …` — протухшее окно молча играет по старым
правилам или не понимает новых флагов.

## 2. Протокол (IPC через файлы)

Каталог — **свой на каждый запуск**: `<tempdir>/colony_watch/<pid>_<мс>/`
(`make_ipc_dir()`; на Windows это `%TEMP%`), удаляется по завершении. Второй и
последующие вызовы в том же процессе добавляют суффикс `_s<N>`: pid+мс
уникальны между процессами, но два запуска подряд могут попасть в одну
миллисекунду и — если предыдущий каталог уже убран — получить тот же путь. Фиксированный общий каталог был
причиной «окно не моё»: UI убивал только `watch_champion.py`, пережившее его
окно продолжало читать `actions.txt`, и следующий запуск общался с сиротой.

| Файл | Направление | Содержимое |
|---|---|---|
| `actions.txt` | драйвер → окно | одно целое число (индекс действия). Окно читает и **удаляет** файл — это сигнал «действие принято» |
| `state.json` | окно → драйвер | `day, month, year, people, bases, money, reward, action, terminated, obs[], action_mask[], minimap[]` |
| `gui_output.log` | окно → лог | stdout+stderr окна (перехватывается драйвером; консоль у watch-процесса скрыта) |
| `ai_debug_gui.log` | окно → диск | отладочный лог C++-стороны (в корне проекта, при включённой отладке) |

**Обе записи атомарны** (`.tmp` → `rename`): `state.json` с миникартой
8×32×32 — это ~100 КБ текста, и драйвер регулярно читал его наполовину
написанным. На Windows `rename` не проходит, пока читатель держит файл
открытым, поэтому C++ делает 5 коротких попыток и откатывается на
`copy_file(overwrite_existing)`.

Два правила, которые нельзя нарушать:

- **Окно удаляет `actions.txt` только после успешного разбора.** Пустой или
  недописанный файл НЕ удаляется: удаление означало бы «прочитано», и стороны
  разошлись бы навсегда (окно открыто, игра стоит, в логе тишина).
- **Драйвер принимает только НОВЫЙ `state.json`** (`state_stamp` = mtime_ns +
  размер). Шаг обязан вычисляться из состояния, которое получилось из
  ПРЕДЫДУЩЕГО действия, иначе на один шаг окна приходится два действия модели.

### Флаги, которые драйвер всегда передаёт окну

```
--headless-ai --actions-file <ipc>/actions.txt --state-file <ipc>/state.json
--seed N --map-size M --tax-to-debt|--tax-dialog
--curriculum '<JSON CurriculumState>' | --curriculum-all
[--reward-config <path>] [--minimap-radius R]
```

`--curriculum` передаётся **всегда** (вычисленное состояние из
`rl/curriculum.py`), чтобы `action_mask` окна не могла молча разрешить
здания другой стадии курикулума.

## 3. Таймауты (все — в `watch_champion.py`)

| Константа | Значение | Что ограничивает |
|---|---|---|
| `GUI_START_TIMEOUT` | 25 с | появление первого `state.json` |
| `GUI_STEP_TIMEOUT` | 30 с | ответ окна на одно действие |
| `GUI_RESET_TIMEOUT` | 20 с | авто-рестарт карты после game over (C++ перезапускает карту сам через 5 с) |
| `GUI_HEARTBEAT_EVERY` | 5 с | как часто в лог UI пишется «жду…» вместо тишины |
| `MAX_GUI_RESTARTS` | 3 | сколько раз перезапускаем упавший exe, прежде чем сдаться |

Константы читаются **в теле** `wait_for_state`, а не в значениях по умолчанию
аргументов: иначе их нельзя подкрутить ни в тестах, ни при отладке медленного
старта окна.

## 4. Что пишет лог в каждой ситуации

Раньше все эти случаи выглядели одинаково — «ничего». Теперь:

| Симптом | Сообщение в логе UI | Причина |
|---|---|---|
| exe не найден | `ERROR: GUI exe not found. Searched: … Build it with build_gui.bat (requires raylib in raylib/), or set COLONY_GUI_EXE=/path/to/gui.exe` | не собран / лежит вне проекта |
| exe падает сразу | `ERROR: GUI-окно не запустилось (exe завершился при старте)` + `exit code N` + хвост `gui_output.log` | `0xC0000135` = не найден DLL (`raylib.dll` рядом с exe); битый `--curriculum` JSON; ошибка в конфиге |
| окно открылось, но молчит | `жду первое состояние от GUI-окна… N с` каждые 5 с, затем `ERROR: … (нет state.json за 25 с)` + `процесс жив, но не пишет state.json` | окно не дошло до игрового цикла (диалог, ошибка инициализации) |
| окно перестало отвечать | heartbeat `жду ответ от GUI-окна…`, затем диагноз и рестарт (≤ 3) | зависание рендера/симуляции |
| модель hybrid, миникарты нет | `ERROR: модель hybrid, но окно не прислало миникарту (нужно 8×32×32 в state.json)` | **протухший exe** — собран до поддержки миникарты в протоколе |
| exe старше исходников | `WARNING: GUI exe собран ДО правок в …` | пересобрать `build_gui.bat` |
| жду авто-рестарт карты | `жду авто-рестарт карты в окне… N с` (до `GUI_RESET_TIMEOUT`) | game over: C++ перезапускает карту сам |
| конец эпизода | `Эпизод N завершён: …` / `Game Over …` | штатно |
| остановка из UI | `Visual watch stopped.` | штатно |

Каждая строка попадает в лог **ровно один раз**: `_log()`/`say()` либо пишут
JSON для UI (`emit_log`), либо печатают текст в консоль, но не то и другое
сразу (раньше панель лога дублировала каждое сообщение).

Остановка из UI убивает **дерево процессов**, а не только `watch_champion.py`:
пережившее драйвер окно и есть «сирота», которая ломает следующий запуск.
На Windows — `taskkill /PID <pid> /T /F`; на POSIX наблюдение стартует с
`start_new_session=True` и останавливается `os.killpg(SIGTERM)` (одиночный
`kill()` ребёнка не доставал). Ручка лог-файла закрывается в UI сразу после
`Popen` — дескриптор у дочернего процесса свой.

## 5. Что считается моделью (частая причина «кнопка ничего не делает»)

`train_ui2/models.py::scan()` показывает в списке прогонов каталог, если в нём
есть **хотя бы один** файл весов:

```
MODEL_WEIGHT_NAMES = ("final_model.pt", "best_model.pt")   # затем checkpoint_*_steps.pt
```

`final_model.pt` пишется **только в конце обучения**, поэтому у остановленного
вручную или упавшего прогона его нет — есть `best_model.pt` и чекпойнты. Раньше
такой каталог не попадал в список, и «👁 Наблюдать» отвечал «Нет моделей —
сначала обучите», что выглядело как «кнопка не работает».

Для запуска `pick_model_file(dir)` берёт `final_model.pt` → `best_model.pt` →
свежайший чекпойнт (это путь UI: «дообучить» и «наблюдать»).
Сам `watch_champion.py` по умолчанию грузит `--model-file best_model.pt`
(чемпион турнира), а если файла нет — `resolve_model_file()` идёт по той же
цепочке: `final_model.pt` → `best_model.pt` → свежайший чекпойнт (и только если
нет ничего, сообщает об ошибке с именем запрошенного файла).

**«Свежайший» чекпойнт — по числу шагов, не по имени.** Лексикографически
`checkpoint_999999_steps.pt` > `checkpoint_1000000_steps.pt`, поэтому
`sorted(...)[-1]` на длинных прогонах возвращал не последний чекпойнт. Порядок
задаёт `train_ui2.models.checkpoint_sort_key()` (общий для UI и CLI); то же
касается sidecar-файлов `checkpoint_*_steps.norm.json`.

Если список всё-таки пуст, диалог теперь сообщает, **где** он искал
(`registry.root`, по умолчанию `~/colony_runs/models`) и какие файлы считаются
весами; то же пишется в лог UI (`WARNING`).

## 6. Как отлаживать вручную

```bash
# 1. собрать C++-окно (не путать с `make gui` — это PySide6-дашборд)
build_gui.bat

# 2. запуск из консоли — весь вывод виден сразу (без UI)
python watch_champion.py --model-dir ~/colony_runs/models/my_run --visual
#    то же через make (консольный режим, без окна):
make watch MODEL_DIR=~/colony_runs/models/my_run

# 3. если exe лежит в нестандартном месте
set COLONY_GUI_EXE=D:\builds\sakhalin_colony_gui.exe   # Windows
python watch_champion.py --model-dir <dir> --visual

# 4. посмотреть, что осталось от прошлого запуска
dir %TEMP%\colony_watch              # каталоги <pid>_<мс>[_s<N>]: actions.txt/state.json/gui_output.log
```

Проверки:

```bash
python -m pytest tests/test_watch_visual.py -q     # протокол, таймауты, диагнозы (без exe: фейковое окно)
python -m pytest tests/test_watch_champion.py -q   # CLI-контракт (нужен собранный colony_cpp)
python -m pytest tests/test_models.py -q           # что считается моделью, выбор файла весов
python -m pytest tests/test_trainer_bootstrap.py -q # контракт obs_mode + связность глобальных имён
./scripts/cpp_checks.sh                            # в т.ч. gui_watch_check (налоговая политика окна)
```

`tests/test_watch_visual.py` гоняет драйвер против **фейкового окна** (Python-
скрипт в роли exe) в режимах `ok / legacy / die / silent / freeze /
no-minimap`, поэтому диагностика проверена без сборки C++ и без raylib.

## 7. Известные ограничения

- Наблюдение однопоточное и lock-step: скорость ограничена самым медленным
  участником (рендер окна или инференс на CPU). `--speed` ускоряет симуляцию в
  окне, но не драйвер.
- `--minimap-radius` у окна сохранён только для совместимости: миникарта
  глобальная 32×32 (см. README §5.3), радиус на наблюдение не влияет.
- `state.json` — текст (~100 КБ на шаг с миникартой). Для длинных прогонов это
  узкое место; бинарный протокол (shared memory) в план не входил.
- Если окно закрыл человек (крестиком), драйвер видит `terminated`/пропажу
  ответа и перезапускает exe — до `MAX_GUI_RESTARTS` раз.
