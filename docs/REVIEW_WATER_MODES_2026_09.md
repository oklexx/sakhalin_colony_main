# Ревью: режимы `flat` / `minimap` / `hybrid` и проблема водоканала

Дата: 2026-09-16 · Ветка: `arena/01a0aae4-sakhalin-colony-main` · Коммит: `70c07d4`

## Вердикт

**Режимы наблюдения работают. Они просто не могут помочь — проблема не в наблюдении.**

- `flat`, `minimap`, `hybrid` корректно собраны по формам и проводят обучение
  (проверено: `tests/test_minimap_hybrid_pipeline.py`, 3 теста, все зелёные).
- Водоканал не строится **не потому, что агент не видит воду**, а потому что:
  1. `WaterChannel` **запрещён маской действий** почти всё время
     (измерено: **0 из 2000** шагов случайного роллаута, 0.00%);
  2. **спам дорогами — это и есть максимум функции награды**
     (измерено: `+898` против `-233` у работающей экономики).

Ни один из этих двух фактов не лечится миникартой, `water_dx/dy` или
distance-shaping.

## Доказательная база

Всё ниже получено запуском **настоящего C++ ядра** (`src/env.cpp`,

### 1. Вода действительно рядом — и водоканал действительно заблокирован


`need_earth=2` = `LT_WATER`: водоканал ставится **на воду**, а не рядом с ней.
Ваше наблюдение «вода недалеко» подтверждено: 7–14 клеток.

### 2. Агент физически не может нацелить дорогу на воду

`find_lot()` (`src/env.cpp:306`) — это BFS от колонии, который **никогда не
читает тип земли цели**. Проверка: две разные карты → одинаковая последовательность
первых 12 дорог:

```
seed 1:   первые 12 дорог заканчиваются у (100,98)
seed 999: первые 12 дорог заканчиваются у (100,98)
```

Действие в пространстве действий — «построй Road», без координат. Клетку
выбирает среда. **Навигации в этом MDP не существует**, поэтому
distance-shaping reward не к чему применить.

Чтобы вода открылась, нужно 83–96 таких слепых дорог (а на seed 100 — **больше
600, и вода так и не открылась**):

```
seed 1    roads_to_water=84    ok=Y
seed 7    roads_to_water=199   ok=Y
seed 21   roads_to_water=157   ok=Y
seed 42   roads_to_water=83    ok=Y
seed 100  roads_to_water=600   ok=N   ← вода недостижима
seed 777  roads_to_water=96    ok=Y
```

### 3. Спам дорогами — это максимум награды

1500 шагов, 3 сида, обычные стартовые деньги:

| Политика | Награда | water | food | wc построен |
|---|---|---|---|---|
| **ROADS ONLY** | **+911.0** | 0 | 0 | 0 |
| Farm, Garden, Road | -224.3 | 0 | 0 | 0 |
| Road → WaterChannel → Farm | +911.0 | 0 | 0 | 0 |
| Water-first («идеальная») | -224.3 | 0 | 0 | 0 |
| House, Farm, Garden, Road | -259.0 | 0 | 0 | 0 |

Обратите внимание на строку 3: политика, в список которой **явно включён**
`WaterChannel`, даёт **побайтово тот же результат, что и чистый спам дорог**
(205 дорог, `wc=0`). Дорога всегда легальна и стоит в списке первой, поэтому до
водоканала очередь не доходит никогда.

### 4. Почему дороги выигрывают: `milestone_base_bonus` считает дороги

Разложение награды по компонентам (штатный `step_log` среды):

```
--- ROADS ONLY (seed 42, 1500 шагов) total=+898.0 ---
   mile       +1241.00     ← доминирующий член
   err         -118.00
   tax         -300.00
   taxb        +109.20
   build         +0.00     ← уже обнулён для дорог
   cost          -8.20

--- FARM ECONOMY (нет воды) total=-387.0 ---
   mile         +41.00
   idle        -120.00     ← штраф «мог строить, но не строил»
   err         -118.00
   tax         -300.00
   build        +30.91
```

`src/game.cpp:759`:

```cpp
int nbases = (int)bases.size();          // ← дороги тоже в bases
if (nbases >= last_base_milestone_ + 5) {
    bonus += milestone_base;             // 30.0 за каждые 5 «баз»
```

206 баз → 41 веха × 30 = **1230**. Совпадает с измеренным `+1241`.
Дорога стоит 400, не требует рабочих, ничего не потребляет и не простаивает —
это идеальный фарм вех.

Последний коммит (`70c07d4`, «zero build bonus for roads») закрыл
`build_bonus` для дорог (`build_r = is_road ? 0.0 : ...`, `src/env.cpp:931`),
но **не закрыл `milestone_base_bonus`** — а он на порядок больше. Утечка
осталась.

Второй фактор: `idle_build_penalty = -2.0` бьёт по экономике (-120), но никогда
по дорогам, потому что Road легален всегда и «нет доступной постройки» не
наступает.

### 5. Вода — реальное узкое место экономики

Та же политика ферм, единственный отличающийся параметр — запас воды:

| Сид | Награда | food |
|---|---|---|

поведение агента не изменит — функция награды всё равно ранжирует спам дорог

## Баги и несоответствия, найденные по ходу

### B1 · Критично · Рассинхрон minimap и flat на границе эпизода

`ColonyVecEnvCpp::step_wait_batch()` делает auto-reset **до** возврата
(`src/env.cpp:1592` → `do_reset(i, new_seed)` → `envs_[i].reset(seed)`), а
`CppVecEnvMinimap.step_wait()` читает миникарту **после**:

```python
def step_wait(self):
    obs, rewards, dones, infos = super().step_wait()   # внутри уже случился reset
    minimap_obs = ... self.cpp_vec.minimap_batch()      # ← карта СЛЕДУЮЩЕГО эпизода
```

На каждом завершении эпизода в буфер попадает пара
`(терминальный flat, стартовая миникарта нового эпизода)`. В режиме `minimap`
весь obs — уже от нового эпизода, хотя награда относится к терминальному
переходу. Это портит обучающие данные ровно на границах эпизодов, т.е. там, где
GAE считает bootstrap.

Проверить вживую здесь не удалось (см. «Что не проверено») — вывод сделан по
чтению обеих сторон контракта.

### B2 · Средне · Режим `minimap` выбрасывает всю экономику

`python/cpp_vecenv_minimap.py`:

```python
if self.obs_mode == "minimap":
    return minimap_obs          # flat-вектор отброшен целиком
```

8 каналов миникарты — это только рельеф (земля/вода/лес/уголь/железо/нефть/
золото/занято). Агент в этом режиме **не знает** ни денег, ни населения, ни
запасов воды и еды, ни цен каталога, ни `water_dx/dy`. Он не может узнать, что
вода на складе кончилась. `exp_25_minimap` и `exp_27_minimap_lr_low` обучаются
именно так.

### B3 · Средне · Разрешение миникарты ниже, чем точность, нужная для дороги

```
map_size=200 → 1 клетка миникарты = 6.25 клетки карты
true water tiles = 37 ; minimap cells flagged water = 4
```

Квант 6.25 клетки при том, что дорога должна подойти к воде **вплотную**
(соседство 1 клетка). Миникарта годится, чтобы понять «вода где-то там», и не
годится, чтобы довести дорогу. Плюс 37 тайлов воды схлопываются в 4 клетки —
форма берега теряется.

### B4 · Мелко · `minimap_radius` — мёртвый и вводящий в заблуждение конфиг

Он лежит во всех трёх конфигах (`exp_25/26/27`, значение 14) и в
`rl/config.py`, но `_make_model()` жёстко передаёт `grid_size=32`, и поле
молча перезаписывается в 15. Заголовок `include/colony/env.h:77` всё ещё
обещает «окно 2R+1 вокруг старта» и возврат `[8, 2R+1, 2R+1]`, докстринг
`rl/actor_critic_cnn.py:13` — «R = 2*minimap_radius+1». Оба не соответствуют
реализации. Изменение `minimap_radius` в конфиге не делает ничего.

### B5 · Мелко · Мёртвая ветка в `proximity_land_for`

`src/rewards.cpp:11`:

```cpp
if (id == "Coalmine" || ... || id == "BigFarm")  return LT_WOOD;   // BigFarm ловится здесь
if (id == "Ironmine" || ... || id == "WaterMill") return LT_OIL;
if (id == "BigFarm")                              return LT_IRON;   // ← недостижимо
```

Там же: `WaterMill` и `PowerStation` дают бонус за близость к **нефти**, а
`WaterChannel` в списке отсутствует вовсе (`grep -c WaterChannel src/rewards.cpp`
→ `0`). Бонус за близость к воде выдан **потребителям** воды (Farm, Garden,
CowFarm, Hothouse, Apiary, Puerperal, Goldmine), но не её **производителю**.

### B6 · Мелко · Латентный in-place баг в GAE

`rl/rollout_buffer.py:131` нормализует преимущества in-place по значению,
производному от них же:

```python
std_adv = self.advantages[:n].std()
self.advantages[:n] = (self.advantages[:n] - mean_adv) / (std_adv + 1e-8)
```

Сейчас не падает только потому, что `async_trainer.py:182` считает
`last_value` под `torch.no_grad()`. Любой вызов `compute_gae` с
`last_value`, у которого есть `grad_fn`, даёт
`RuntimeError: ... modified by an inplace operation`. Я на это наткнулся,
пока писал тест. Лечится оборачиванием `compute_gae` в `no_grad` или
`adv = adv.detach()` перед нормализацией.

### B7 · Мелко · Курикулум в конфигах не ограничивает ничего

`exp_25/26/27` все выставлены в `curriculum_stage: 0`, а
`ids_for_stage(0, None)` возвращает `list(ALL_IDS)` — все 32 постройки.
Курикулум в этих экспериментах фактически выключен, так что сравнивать режимы
наблюдения между собой они не мешают, но и «план курикулума» через них не
проходит.

## Что реально стоит сделать

В порядке убывания эффекта:

1. **Исключить дороги из `milestone_base_bonus`.** `src/game.cpp:759` — считать
   только постройки с `id != ROAD_ID`. Это убирает главный стимул к спаму
   дорог. Без этого пункта всё остальное — косметика.
2. **Дать агенту управление размещением.** Пока клетку выбирает `find_lot()`,
   ни миникарта, ни `water_dx/dy`, ни любой distance-shaping не имеют канала
   влияния на поведение. Минимальный вариант — направление следующего
   расширения дороги (4 действия N/S/E/W) вместо «построй Road».
3. **Не штрафовать `idle_build_penalty`, когда легален только Road**, либо
   считать Road «не строительством» и для этого штрафа тоже — иначе любая
   осмысленная политика проигрывает дорожному спаму ещё и на этом члене.
4. **Починить B1** — читать `minimap_batch()` до auto-reset (или возвращать
   миникарту из `step_wait_batch` вместе с flat). Без этого `minimap`/`hybrid`
   обучаются на частично неверных данных.
5. **Вернуть экономику в режим `minimap`** (или отказаться от него в пользу
   `hybrid`) — B2.
6. **Поднять разрешение миникарты или дать координатный хвост** — при кванте
   6.25 клетки довести дорогу до воды нельзя (B3).
7. Мелочи: B4 (удалить мёртвый `minimap_radius` и поправить доки), B5
   (добавить `WaterChannel`, убрать мёртвую ветку), B6 (`no_grad`), B7
   (выставить реальные этапы).

Отдельно: починка воды сама по себе **не** развернёт агента к экономике —
пункт 5 таблицы из раздела 3 показывает `-213` у работающей фермерской
политики против `+898` у дорожного спама даже при бесконечной воде.

# Дополнение 3: какие правки к какому режиму относятся

## Матрица применимости

| Правка | Где живёт | `flat` | `minimap` | `hybrid` |
|---|---|---|---|---|
| R1 milestone без дорог | `src/game.cpp` (ядро) | ✅ | ✅ | ✅ |
| R2 гейт `idle_build_penalty` | `src/env.cpp` (ядро) | ✅ | ✅ | ✅ |
| R3 мёртвая ветка proximity | `src/rewards.cpp` (ядро) | ✅ | ✅ | ✅ |
| ROAD_E/W/S/N (45→49 действий) | `src/env.cpp` (ядро) | ✅ | ✅ | ✅ |
| B1 порядок чтения миникарты | `python/cpp_vecenv_minimap.py` | — (миникарты нет) | ✅ | ✅ |
| B6 `detach` в GAE | `rl/rollout_buffer.py` | ✅ | ✅ | ✅ |

Пять из шести правок — в C++-ядре среды, поэтому они применяются ко всем трём
режимам одинаково. B1 относится только к режимам с миникартой.

## Так ли, что «верно работает только hybrid»?

**Нет. Корректны два режима из трёх: `flat` и `hybrid`. Сломан `minimap`.**

- **`flat`** несёт полную экономику **и** `water_dx/water_dy`. Проверено на
  обоих раскладках obs:
  ```
  obs_version=0: obs_size=248  water_dx=+0.0000 water_dy=-0.0350  → (0,-7) клеток
  obs_version=1: obs_size=289  water_dx=+0.0000 water_dy=+0.0350
  ```
  Миникарты у него нет, поэтому B1 к нему просто не относится — там нечему
  рассинхронизироваться. Для навигации к воде ему хватает `water_dx/dy`.

- **`hybrid`** = `flat` + 8×32×32 миникарта. Строго больше информации, чем
  `flat`, плюс B1 теперь закрыт.

- **`minimap`** — единственный проблемный: `_get_obs()` возвращает **только**
  миникарту, flat-вектор отброшен целиком. Агент не видит ни денег, ни
  населения, ни запасов воды/еды, ни `water_dx/water_dy`. Направленные дороги у
  него есть, но целиться он может лишь по рельефу с квантом **6.25 клетки**
  (37 тайлов воды схлопываются в 4 клетки), тогда как дорогу нужно подвести
  вплотную (соседство 1 клетка).

Практический вывод: `hybrid` — основной режим, `flat` — корректная и более
дешёвая база для сравнения, `minimap` — только как абляция «решается ли задача
одним рельефом».

## Что пришлось доделать вслед за сменой пространства действий

Смена 45 → 49 всплыла в трёх местах, где список имён действий дублировался
вручную и обрывался на `PAY_TAX`:

| Файл | Было | Стало |
|---|---|---|
| `rl/async_trainer.py` | fallback-список из 45 имён | + `ROAD_E/W/S/N` |
| `python/cpp_env.py` | `_action_names` из 45 | + `ROAD_E/W/S/N` |
| `tests/test_async_trainer.py` | `assert len(names) == 45` | `== 49` + проверка хвоста |

Тест `test_async_trainer.py` раньше **закреплял** устаревшее число 45, поэтому
он бы молча «защищал» неправильный контракт.

В `watch_champion.py`, `train_ui2/`, `ui/` и `src/gui.cpp` хардкодов числа
действий нет (проверено grep'ом) — GUI работает через `A_BUILD0 + i` и
`n_actions()` из среды.
